# 改规矩

规矩文件是给以后的 Claude 读的。它越长、越重复，越容易被读漏；两条说法打架时，Claude 会随便挑一条。所以改规矩的目标不是「把新经验加进去」，而是**改完以后，规矩还是一份短、不打架、每件事只说一遍的说明书**。

## 一、先分类：这次的东西属于哪一种

分类前先问一句：**这条是在规定结果，还是在规定过程？**规定过程的，先想能不能改成检查结果（写成「验收」）。只有结果查不出来、或者必须每次一模一样的事，才写成固定步骤。

| 是什么 | 例子 | 放哪 | 怎么写 |
|---|---|---|---|
| **数字 / 参数** | 停顿 0.45 秒、音量 -14 LUFS、超时 30 秒 | **程序里**（脚本默认值、config 文件）只放一处 | 程序里紧挨着数字写一行「为什么是这个数、哪天谁定的」。规矩里只写「这件事由某程序管，数字在某文件」，**不抄数字** |
| **规矩** | 「每期都配音」「事实都要有出处」 | 这件事唯一的「家」（见第二节） | 新的**替换**旧的；一两句话，带半句「为什么、防的是哪件事」 |
| **接口 / 约定** | 模块之间交什么文件、什么格式；在哪几处停下来等人看 | 总入口（主 CLAUDE.md 或总入口 skill）一处 | 写死。改的时候所有用到它的模块当场一起改 |
| **做法 / 招** | 某种画面做法、某种开头写法、某个好用的组合 | 工具箱或参考文件，**不进规矩正文** | 写成可选的例子：哪次用过、为什么那次好使、什么时候别用。不写「必须用」 |
| **验收** | 量响度、遮住字幕看画面懂不懂、子 agent 审片 | 流程里那一道关 | 写「查什么、过线标准」，不写「怎么做到」。为了省返工的提前检查（先出 10 秒小样）也算验收，写「什么时候先验一下、验什么」 |
| **经历** | 用户某天的原话、选了哪版样片、某次踩的坑 | 日志类文件（口味档案、复盘、决策记录），**按日期往下记** | 只追加不改。被后来的决定推翻时，只在旧条目后补一句「→ 已被 某日 取代」 |

拿不准时：**一次的感觉是经历，不是规矩。**没验证过的猜测（「下次大概放到 0.3 秒」）不进规矩，写成「下次先做对比小样」，用户选定后再把结果写进程序或规矩。一次好使的做法是「招」，不是规矩。

**口味类日志分两半**：上面是按日期只追加的原始记录；另有一段「现在的口味」汇总，**替换着维护**，每条后面带出处日期。平时默认只读汇总，要查来由时才翻原始记录。每次往原始记录加一条，顺手检查汇总要不要改。

## 二、找家：这件事现在写在哪

1. 先看项目有没有「东西放在哪」的地图（通常在主 CLAUDE.md 或总入口 skill 里）。有就照它找。
2. 再全文搜关键词和同义词（例：停顿 / 句间 / 间隔 / pause / gap；配音 / 不配音 / 人声 / 只有音效），把**所有**提到这件事的地方列出来，包括程序注释、模板、交接文档。
3. 定一个「家」：最贴近这件事、别人最先会读到的那一处。其他地方只能留一句指针（「见 某文件 第几节」），或者删掉。
4. 项目还没有地图时，在主 CLAUDE.md 里建一张很短的表：「什么事 → 在哪个文件」。

## 三、改：替换，不追加

- 在「家」里**直接改写**那条规矩，让它读起来就像一开始就是这么定的。
- **不写修改史**：不写「（某日改，原来是……）」「第二版」「以前是 X 现在是 Y」。历史在 git 和日志里，规矩只写现在怎么做。日期只留在「谁拍板的」这种必要处，而且只留最新一个。
- 别处的旧说法：改成指针或删掉。**改一处，所有地方当场跟着改**，不留「以后再清」。
- 旧数字从规矩文字里删光；数字只在程序里。
- 不加「重要」「一定」「必须」来强调。一条规矩反复被忽略，说明文件太长或者它该交给程序 / hook 去强制。
- 改完再搜一遍旧关键词，确认规矩文件里不再出现过时的说法（日志里出现没关系）。

## 四、给用户看

改完用三行报告，不贴大段 diff：

```
改了：<家>：<旧说法> → <新说法>
跟着改：<文件1>（改成指针）、<文件2>（删掉）……
记进日志：<日志文件> <日期> 一条（用户原话）
```

改主 CLAUDE.md、全局 CLAUDE.md 这类每次都加载的文件，先把要改的那句给用户看，同意再写。

## 五、体检（用户说「体检」，或做完一个大阶段时主动问要不要做）

1. 列出项目里所有规矩类文件和每份的行数；单份超过约 200 行的标出来。
2. 逐条找五种病：
   - **重复**：同一件事写在两处以上。
   - **打架**：两处说法不一致，或一个鼓励、一个禁止。
   - **过时**：已经被后来的决定推翻、已经到期的一次性安排（「下一期试一次 X」而那一期已经做完）、指向不存在的文件。没写为什么、或看不出在防哪件事的规矩，算**过时嫌疑**。
   - **写死**：规矩文字里抄着具体数字，数字又在程序里另有一份。
   - **管太死**：在规定过程，其实检查结果就够了；或者给创作、审美类的事定了唯一做法（一次好使的做法被写成了每次必须）。建议改成「验收」或移进工具箱当「招」。
3. 有官方命令可用时，加跑一次 `/doctor prompt-audit` 作为第二意见。
4. 交给用户的是一张清单：每条写「哪两处 / 什么病 / 建议怎么改」。**只列不改**，用户一条条定，定了再按第三节改。
5. 可选：**删减测试**。怀疑某条规矩已经多余（尤其是换了更强的模型以后），拿同一段素材做 A/B 两版，只差这一条规矩；先让没参与制作的子 agent 盲评，分不出高下的再交给用户盲选。没变差就删。规矩文件开头记一行「上次删减测试：哪个模型、哪天」，体检时发现模型变了，提醒用户一次。

## 六、写规矩的几个习惯

- 一条规矩只说一件事，先说做什么，再用半句说为什么。
- 能交给程序的（数字、格式检查、必须每次跑的命令），交给程序；规矩里只指过去。
- 例子写一个就够；更多例子放日志或参考文件。
- 规矩之间有先后时写清楚谁优先（「和某文件冲突时，以某文件为准」），只写一次。
